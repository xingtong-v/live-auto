# live_auto —— B站直播全自动切片系统

从直播开播到切片投稿的**全无人值守**流水线。

```
直播开播 → 自动录制（视频+弹幕） → 自动压制/转封装 → 自动上传完整版录播
        → 自动语音转写 → 自动总结本场内容 → 自动选取高价值片段、生成标题简介
        → 自动切片并投稿（多个切片错峰定时发布、归入同一合集）
```

**除 B站 cookie 过期需人工扫码外，全流程无人工干预。** 提供半自动（默认）/ 全自动双模式。

## 30 秒上手

**方式一：双击桌面快捷方式**（已创建）

桌面上的「**直播切片助手**」快捷方式会自动完成：检查环境 → 启动后端 → 打开界面（Edge 应用窗口，无地址栏标签页，像个独立应用）。关闭那个窗口即停止服务。

**方式二：命令行**

```powershell
# 1) 生成配置（从 biliLive-tools 的配置里读取 PassKey，不会打印到屏幕）
node tools/init-config.mjs

# 2) 只读探测：验证接口连通、记录实测响应，不产生任何费用
node src/probe.ts --dry-run

# 3) 启动自检（逐项给出可执行的修复建议）
.\start.ps1 -SelfCheck

# 4) 常驻运行（半自动模式，浏览器打开 http://127.0.0.1:3000）
.\start.ps1
```

**方式三：开机自启（设置一次，以后不用管）**

```powershell
# 安装/更新（双击 tools\autostart.cmd 同样效果）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\autostart.ps1 -Install
# 查看状态（任务是否注册 + 服务是否在跑 + 上游 biliLive-tools 是否也自启）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\autostart.ps1 -Status
# 取消自启（不影响正在运行的服务）
powershell -NoProfile -ExecutionPolicy Bypass -File tools\autostart.ps1 -Remove
```

它注册的是一个**计划任务**（不是注册表 Run），所以能带上这几样东西：
登录后**延迟 30 秒**启动（让上游 biliLive-tools 和网络先就绪）、**有窗口**（和双击快捷方式一样能看见启动日志与报错；
加 `-Hidden` 可切成后台静默，加 `-Browser` 则连界面一起打开）、
**只允许一个实例**（避免重复启动撞端口）、**失败自动重试**（3 次 / 间隔 1 分钟）、
以及**看门狗**：每 10 分钟检查一次服务在不在，不在就拉起来（`-WatchdogMinutes 0` 可关）。
全程**不需要管理员权限**（以当前用户、受限级别运行），启动日志在 `data/logs/launcher-console.log`。

为什么要看门狗：自启只在登录时跑一次。实测 2026-09-24 12:07，正在跑的进程被外部以
「Ctrl+C 式」终止（任务计划程序的"失败重试"对**被外部终止**不生效），服务就再没自己回来。
看门狗每一跳只是 `launcher.ps1` 的第 0 步检查（3 秒 HTTP 探测）—— 服务健在时立刻退出，几乎零开销。
实测：`12:11:58` 杀掉服务 → 什么都不做 → `12:12:51` 看门狗按时触发 → 服务自动上线（等待 42 秒）。

**想让它停下来的三种粒度**（因为看门狗会把被杀掉的服务拉回来）：

| 目的 | 命令 |
|---|---|
| 临时停（保留自启，看门狗也停） | `Disable-ScheduledTask -TaskName '直播切片助手（live_auto）'`；恢复用 `Enable-ScheduledTask` |
| 只停服务（下次登录或看门狗还会拉起） | 在启动器窗口按 Ctrl+C，或结束占用 3000 端口的进程 |
| 彻底取消自启 | `tools\autostart.ps1 -Remove`（正在运行的服务不受影响） |

> 窗口模式的取舍：默认**有窗口**（能看见日志，也能一眼确认它在跑）。关掉那个窗口 = 停服务，
> 而看门狗会在 10 分钟内**再弹一个窗口**把它拉起来 —— 所以"想停久一点"请用上面的
> `Disable-ScheduledTask`，不要只是关窗口。启动器保留 `-NoPause` 是刻意的：出错时窗口随手关掉、
> 错误全在 `data\logs\launcher-console.log` 里，而任务能正常结束 → 看门狗下一跳还能重试；
> 若停在"按任意键"，任务会一直处于 Running，看门狗反而不重试了。

> ⚠️ 触发时机是「**登录时**」——机器停在锁屏没登录时不会启动。要连登录都不需要，
> 得用「计算机启动时」触发器 + 保存账户密码，那一步需要管理员权限，本项目默认不做。
>
> biliLive-tools 自己已经注册在 `HKCU\...\Run`（`--hidden`）里 —— 上游会一起起来，
> 所以本服务开机后能直接接上录制与上传；即使它还没起来，本服务也会照常常驻，
> 等它就绪后自动恢复（健康面板会如实显示"未连接"）。

## 环境要求

| 项 | 要求 | 说明 |

.\start.ps1 -Node "F:\deepseek\node\node.exe"

## 配置

复制 `config.example.json` 为 `config.json`（或用 `node tools/init-config.mjs` 自动生成）。
`config.json` 含凭据，**已在 `.gitignore` 中，切勿提交或分享**。

> 环境变量可覆盖关键项，便于不落盘地注入凭据：
> `LIVE_AUTO_BILILIVE_PASSKEY`、`LIVE_AUTO_BILILIVE_URL`、`LIVE_AUTO_ROOM_ID`、
> `LIVE_AUTO_LLM_KEY`、`LIVE_AUTO_LLM_MODEL`、`LIVE_AUTO_AUTO_PUBLISH`、`LIVE_AUTO_LOG_LEVEL` 等。

### AI 配置（必做，否则转写与分析会失败）

**① 转写（ASR）：在 biliLive-tools 里配置**

1. 打开 biliLive-tools → 设置 → **AI 配置** → 供应商
2. 添加阿里云供应商并填入 AccessKey（**建议用 RAM 子账号、最小权限**，而非主账号）
3. 在「模型」中新增模型，**标签勾选 `ASR`**（例如阿里云 `fun-asr`）
4. 为「字幕识别」指定该模型

> ⚠️ 没配置 ASR 模型时，`POST /ai/subtitle` 会**直接抛错**「请先在配置中设置字幕识别ASR模型」。

**② 内容分析（LLM）：在本项目里配置**

在 Web UI 的「设置 → AI 配置」或直接编辑 `config.json`：

```jsonc
"llm": {
  "preset": "deepseek",
  "summary": {                        // 便宜档：分块要点 + 全局总结（约 20 次调用，占绝大部分 token）
    "baseUrl": "https://api.deepseek.com/v1",
    "apiKey": "sk-...",
    "model": "deepseek-chat"
  },
  "select": {                         // 选片专用档：选片 + 起标题（每场 1–2 次，最考验能力）
    "baseUrl": "https://api.deepseek.com/v1",
    "apiKey": "sk-...",
    "model": "deepseek-reasoner"      // 留空则用 summary 的模型
  }
}
```

> ⚠️ **两档建议配成不同模型**。若配成同一个，「契约校验失败 → 升级模型重跑」会退化为
> 「同模型重试一次」，升级机制失效。UI 会在这种情况下给出提示。

供应商预设（UI 下拉可一键切换）：DeepSeek（推荐）/ 阿里云百炼通义千问 / 智谱 GLM-Flash（有免费档）/ 本地 Ollama / 自定义。

### 关键配置项

| 配置 | 默认 | 说明 |
|---|---|---|
| `room.roomId` | — | 目标直播间房间号 |
| `room.platform` | `Bilibili` | **必须首字母大写**。写成 `bilibili` 会静默返回空数组，触发永不生效 |
| `room.offlineConfirmSec` | 600 | **下播确认窗口**。断流时第一段也会「看起来结束了」，必须持续非直播 ≥ 该值才判定本场结束 |
| `publish.autoPublish` | `false` | `false` = 半自动（需在 UI 勾选确认）；`true` = 全自动 |
| `publish.isOnlySelf` | `1` | 仅自己可见。**试跑期必须保持 1** |
| `publish.submitGapSec` | 7800 | 首片相对提交时刻的余量，**必须 > 7200** |
| `publish.clipGapSec` | 7500 | 相邻切片间隔（保守余量，非平台硬性要求） |
| `publish.dailyLimit` | 5 | 每日投稿上限（试跑期建议 2–3） |
| `publish.seasonId` | 0 | **合集 ID。没有任何接口能创建合集**，需在 B站创作中心手动创建后填入；留空则切片不会归入同一合集 |
| `publish.defaultCategory` | `游戏/单机游戏` | 分区回退值（`tid` 只能来自白名单） |
| `publish.aiNotice` | 两行：AI 声明 + 求赞 | **投稿简介末尾的 AI 声明**（可多行）。默认 `本视频由 AI 完成选段、字幕与自动投稿，内容来自直播回放，发布前未经人工确认` + 一句求赞。声明最后拼、**不参与 250 字符截断**（否则正文一长就被截掉），单切片/多分P 稿件/我们上传的完整版都会带上；留空 = 不写 |
| `publish.multiPart` | `false` | `true` = 一场直播只占 **1 个投稿额度**（P1 完整版 + P2 纯享版 + P3… 切片） |
| `publish.resumeAid` | 空 | 续传目标稿件的 **aid**：切片追加进 biliLive-tools 那个稿件的分P，而不是新建稿件（见「五、续传」） |
| `publish.resumeTitleTemplate` | `{anchor}{liveTitle}{date}` | 自动查续传目标用的标题模板，须与 biliLive-tools 的 `{{user}}{{title}}{{now}}` 对齐；留空 = 关闭自动查找 |
| `clip.fullVideoHasDanmaku` | `false` | 源文件是否已烧弹幕。**不允许运行时猜测**，否则可能叠双层弹幕 |
| `cleanup.retentionDays` | 7 | 切片全部发布且完整版确认后的缓冲期 |
| `cleanup.diskFloorGB` | 50 | 磁盘守卫阈值，低于此值停止新任务并告警 |
| `alert.channels` | `[]` | 告警渠道：`serverchan` / `dingtalk` / `telegram` / `webhook` |

## 使用

### 命令行

```powershell
# 常驻运行（轮询 + Web UI）
node src/cli.ts run

# dry-run：只到 clips.json + 摘要，不切片不投稿，且默认不调用付费 AI
node src/cli.ts run --dry-run

# 显式允许产生费用（dry-run 下也要显式给）
node src/cli.ts run --dry-run --allow-paid

# 跑一次检查就退出（适合计划任务）
node src/cli.ts once

# 离线模式：直接对一条历史录播跑完整链路（无需等开播）
node src/cli.ts video "D:\rec\sample.flv" --danma "D:\rec\sample.xml" --dry-run

# 从指定阶段重跑某一场（已缓存的转写会复用，不重复付费）
node src/cli.ts replay 20250922-2130-ab12cd34 --from-stage ANALYZED

# 查看错误报告（不需要复现就能定位问题）
node src/cli.ts inspect 20250922-2130-ab12cd34

# 其它
node src/cli.ts health        # 健康快照
node src/cli.ts selfcheck     # 逐项自检
node src/cli.ts clean --dry-run # 预览将清理哪些素材
node src/cli.ts perf          # 拉取稿件表现数据
node src/cli.ts probe         # 接口联调探测
```

### 启动脚本

| 脚本 | 用途 |
|---|---|
| `run.cmd` | **一键启动**（桌面快捷方式指向它）：检查环境 → 启动后端 → 打开界面 |
| `launcher.ps1` | 上面那个的实际逻辑，可带参数运行 |
| `start.bat` / `start.ps1` | 等价入口（`start.bat` 也转调 `launcher.ps1`） |

```powershell
# 一键启动（等价于双击桌面快捷方式）
.\run.cmd

# 带参数：dry-run 且不开界面
.\run.cmd -DryRun -NoBrowser

# 换端口（3000 被占用时）
.\run.cmd -Port 3100

# 等价入口
.\start.bat
.\start.ps1 -DryRun              # dry-run
.\start.ps1 -Once -Room 12345678 # 跑一次检查
.\start.ps1 -SelfCheck           # 只自检
.\start.ps1 -Probe               # 只探测接口
.\start.ps1 -NoUi                # 不启动 Web UI（适合注册为 Windows 服务）
```

`launcher.ps1` 的可选参数：`-DryRun`、`-AllowPaid`、`-NoBrowser`、`-Port <端口>`、`-Room <房间号>`、`-NoPause`。

> ⚠️ **维护提示：`.bat` / `.cmd` 文件必须用「纯 ASCII + CRLF 换行」**
> `cmd.exe` 按系统 ANSI 代码页读取脚本内容，且要求 CRLF 行尾。如果这两个条件不满足：
> - 中文注释会被错误解码，**注释行被切断后，剩下的片段会被当作命令执行**
> - 只写 LF 会让行边界错乱，报出一串 `'xxx' 不是内部或外部命令`
>
> 现象很有迷惑性：脚本看起来"部分能跑"，但错误全是莫名其妙的外部命令。本项目为此踩过一次坑，
> 所以 `run.cmd` / `start.bat` 里刻意不含任何非 ASCII 字符。
> 需要中文提示时，让它们转调 `.ps1`（PowerShell 脚本用 **UTF-8 带 BOM** 保存，PS 5.1 才能正确解析中文）。

> 若快捷方式被误删，重新创建：
> ```powershell
> $ws = New-Object -ComObject WScript.Shell
> $sc = $ws.CreateShortcut("$([Environment]::GetFolderPath('Desktop'))\直播切片助手.lnk")
> $sc.TargetPath = 'F:\deepseek\live_auto\run.cmd'
> $sc.WorkingDirectory = 'F:\deepseek\live_auto'
> $sc.IconLocation = 'F:\deepseek\live_auto\app.ico,0'
> $sc.Save()
> ```

### 两种模式

- **半自动（默认，`autoPublish: false`）**：分析完成后推通知并在 UI 待审，人工勾选确认后才发布。
- **全自动（`autoPublish: true`）**：分析完成后按评分阈值自动选片、自动切片、按 ≥2 小时间隔排期发布。

首次部署**必须用半自动**，确认选片质量稳定后再改全自动。UI 顶栏有开关可随时切换。

### 状态机

```
IDLE → RECORDED → TRANSCRIBED → ANALYZED → CLIPPED → PUBLISHED
```

每阶段产出落盘在 `data/tasks/<taskId>/`：

| 文件 | 内容 |
|---|---|
| `trigger.json` | 触发证据（为什么判定本场结束、分段映射） |
| `transcript.json` | 转写（`[{start, end, text}]` + `gaps` 缺失区间） |
| `signals.json` | 弹幕信号（密度曲线、峰值、热词、高能事件、时间基准偏移） |
| `summary.md` | 本场总结（Markdown） |
| `clips.json` | 候选切片（含 LLM 评分、理由、降级标记） |
| `<视频名>-proj.llc` | 可在 biliLive-tools 切片界面打开精修的项目文件 |
| `events.jsonl` | 本场事件流水 |

## 任务操作（删除 / 停止 / 重跑）

任务卡以前只能看不能动 —— 进程被强杀后任务会永久停在「切片中」，用户唯一的出路是手改 `data/ledger.json`。
现在所有任务操作都在界面上有两个入口，效果完全一样：

- **左侧任务卡片的「⋯」按钮**，或直接在卡片上**右键**；
- **详情页顶部的「任务操作」栏**（打开某个任务后就在最上面）。

| 操作 | 说明 |
|---|---|
| 查看详情 | 切到该场次的中栏详情 |
| 停止处理 | 仅对「正在处理」的任务出现；把它移出队列并把状态修回可操作状态（biliLive-tools 里已在跑的 ffmpeg 会自己跑完） |
| 从某阶段重跑… | 可选 ANALYZED（重跑 LLM 选片）/ TRANSCRIBED（复用转写缓存，不再付费）/ RECORDED（从源素材重来）/ CLIPPED（重新切片与投稿） |
| 复制全部稿件链接 | 把本场已投稿件的「标题 + 视频地址」一次性复制到剪贴板（仅当有已投稿件时出现） |
| 打开 B站 稿件管理 | 打开创作中心稿件管理页 —— **下架已投稿件只能在这里做** |
| 复制任务 ID / 打开产物目录 | 便于命令行重跑与去资源管理器看产物 |
| 刷新稿件表现数据 | 已发布任务可拉取播放/点赞等数据回流 |
| 删除任务… | 先弹**删除预览**，看清会释放多少空间，再勾选确认 |

### 删除任务：先预览，再确认

删除是不可逆的，所以接口与界面都强制两步：

```
GET  /api/task/:id/delete-plan   → 列出「切片产物 / 任务目录 / 源素材」各自多少 MB、哪些文件被其它任务共享
POST /api/task/:id/delete        → 必须带 confirm:true，否则 400
```

三个删除范围互相独立，默认**只删切片产物**（最占地方且随时可重切）：

| 范围 | 内容 | 注意 |
|---|---|---|
| 切片产物 | `data/clips/<taskId>/` 下的成片 | 可随时按 `clips.json` 重切 |
| 任务目录 | 转写 / 弹幕信号 / 总结 **＋ `full/` 下的压制产物** | 预览里会把这两块**分开报体积**：大头通常是压制产物（弹幕版 + 纯净版，实测一场 23 分钟的直播约 2.9 GB），转写等文本文件只有几 MB |
| 源素材 | 录制原始分段 | 被其它任务共享时自动锁定并说明原因 |

> ⚠️ **本地删除不会撤回 B站 上已投稿件。** 删除接口只删本地记录与文件，返回值与界面都会明确提示；
> 真要下架稿件必须去 B站创作中心，所以菜单里给了「复制全部稿件链接」和「打开 B站 稿件管理」两个入口。

另外两个接口服务于「任务卡死」场景：`POST /api/task/:id/stop`（停止并修状态）、
`POST /api/tasks/repair-stuck`（顶栏「修复卡住」，把 running 态任务按切片证据修回稳定态）。

### 切片级操作：在「发布排期」栏里直接改 / 删

排期栏（右栏）原来只是只读列表 —— 看到不想要的一片，得先切到那一场的详情页，
而「删掉这一片」根本没有入口。现在每一片都带三个动作：

| 动作 | 行为 | 接口 |
|---|---|---|
| 编辑 | 切到该场详情页（那里有完整的标题/区间/标签/勾选编辑器） | —— |
| 改发布时间 | 弹时间输入框，手填的发布时间**盖过自动排期**，也盖过全局的「立即发布」；留空保存 = 回到自动排期 | `PATCH /api/task/:id/clip/:idx` 带 `dtime` 或 `clearDtime` |
| 删除 | 从本场清单里移除这一片（**不删成片文件**，也不影响 B站 上已有稿件） | `POST /api/task/:id/clip/:idx/delete` |

几条必须记住的约束（都写在代码与测试里）：

- **硬约束 #4 一步不让**：手填的发布时间必须 > 提交时刻 + 7200 秒，否则接口返回 400 并给出
  `earliestAllowed`（界面直接提示「最早可选 …」），**不会**悄悄按不合规的时间投出去让 B站 拒稿；
- **已投稿的切片不能删**：接口返回 409 并说清「删本地记录不会把稿件从 B站 撤下来」——
  要撤只能去创作中心；
- **删除不重排 index**：`index` 是台账 / `decisions.jsonl` / 幂等指纹 / 界面共用的稳定标识，
  删一条就把后面的号全挪一遍会让已有记录指向错误的切片；所以只摘掉那一条，其余原样保留；
- **删除会连带清掉该片的幂等指纹**：不清的话，重新分析又选出同一区间时会被判成「已投过」而
  **静默跳过**（少投一稿且没有任何提示）；
- **多分P 模式下逐片排期不生效**：整个稿件只有一个 `dtime`，排期栏会直接提示这一点。

验证：`npm run clip-actions-test`（28 项：删除语义 / 指纹清理 / `unset` 清空字段 / 时间解析与 #4 边界）、
`npm run ui-e2e`（真浏览器点一遍三个动作，含「不合规时间被拒」与「清空回到自动排期」）。

## 字幕烧录与术语表

### 字幕：转写结果烧进画面（默认开启）

转写本来就花过 ASR 的钱，之前只用来选片、**没有烧进画面**，等于白花一次。
现在 `clip.burnSubtitles`（默认 `true`）会把 `transcript.json` 变成 ASS 并与弹幕合并后一起烧。

**为什么是「合并」而不是传两个 ASS**：实测 `POST /task/cut` 的 `files` 只接受**一个** `assFilePath`：

```js
const files = { videoFilePath };  if (assFilePath) files['assFilePath'] = assFilePath;
```

所以字幕事件被写进**弹幕 ASS 本体**（继承它的 `PlayResX/PlayResY`、`WrapStyle` 与样式表），
只新增一个 `Subtitle` 样式：字号更大、`Alignment=2` 底部居中、
`Outline=3` 实描边（花哨的直播画面上没有描边的白字读不出来）、
`MarginV` 比弹幕底部样式更大 —— 两者不会叠在一起。

| 配置项 | 默认 | 说明 |
|---|---|---|
| `clip.burnSubtitles` | `true` | 关掉就只烧弹幕（**当前实机为 `false`**，见下一节） |
| `clip.subtitle.fontSize` | `0` | 0 = 按分辨率推算（1080p 约 49px） |
| `clip.subtitle.maxCharsPerLine` | `18` | 中文折行宽度，超过折第二行（最多两行） |
| `clip.subtitle.minDurationSec` | `0.8` | ASR 碎片一闪而过看不清，会被补到这个时长 |
| `clip.subtitle.fontName` | `Microsoft YaHei` | 字体 |

落盘位置：`data/tasks/<taskId>/burn-<指纹>.ass`（与弹幕合并后）。
文件名带内容指纹，同一场重复切片复用同一个文件；改转写或改参数自然生成新文件。

### 暂时关掉字幕时，仍然要做的一道护栏：能量边界修正

2026-09-24 实机把 `clip.burnSubtitles` 设为 `false`（弹幕照烧）。原因是云 ASR 的**段级时间戳**
在这类"背景一直在响"的直播上会离谱（实测「如。萌啊…」15 个字占 0→30.9 秒），
字幕因此会挂在没人说话的时刻；要修得准就得上本地 ASR，代价不划算，所以先不做字幕。

**但关掉字幕躲不掉一半问题**：切片边界是**按 ASR 段边界吸附**的
（`analyze.ts` 的 `snapStartToSpeechBoundary`），ASR 的窗口错，边界就跟着错 ——
实测 `clip[1]` 的起点 `746.69s` 正好等于那条假窗口的开头，成片**前 29 秒只有背景音**
（响度 −31…−38 dB），观众看到的是空转。

所以加了 `clip.boundarySpeechTrimSec`（默认 30，0 = 关闭）：

- 用**音频能量**（本地 ffmpeg 解 8kHz 单声道算 RMS，零费用、与 ASR 无关）判断"这段时间有没有人说话"；
- 起点/终点落在没人说话的地方时，把它拉到最近的人声位置；
- **只在死气超过 4 秒时才动**（正常开场留白实测 2.5 秒，不该裁），且保证裁完不低于时长下限；
- 拿不到剖面或开关为 0 时行为与旧版完全一致（可一键回退）。

实测（同一场、两片）：

| 切片 | 起点 | 结尾 |
|---|---|---|
| `clip[1]`（前 29 秒空转） | 746.7s → **776.0s**（裁掉 29.3 秒） | 903.3 → 903.5（死气 0.5s，不动） |
| `clip[0]`（正常） | 307.0 → 309.5（死气 2.5s，**不动**） | 516.0 → 516.5（不动） |

> ⚠️ 这里踩过一个坑：第一版用"区间能量的**中位数**"当背景电平，结果在"窗口里大部分时间本来
> 就是人声"时，阈值被抬到人声之上 → 结尾修正静默失效。现在改用 **20 分位**估计背景电平。
> 回归用例见 `npm run clip-boundary-test` 场景 11。

### 术语表：纠正 ASR 听错的人名与术语

直播里人名、游戏术语、圈内梗是通用 ASR 的固定短板，错了会一路传下去：
转写错 → 选片看不懂 → 标题里专有名词写错 → 观众一眼看出是机切的。

**为什么不做「热词直传 ASR」**：查过基础设施的实际契约 ——
`POST /ai/subtitle` 的请求体只有 `file / modelId / startTime / endTime / offset / song` 六个字段
（在 biliLive-tools 的 `app.asar` 里核对过 `subtitleRecognize` 实现），
**没有热词入参**，且硬约束 #1 禁止改它。所以走两条等效但可控的路：

1. **转写后确定性纠错**（`replacements`）：`错→对` 逐条替换，先写的先生效，支持 `re:` 正则。
   这是热词最实在的那部分收益 —— 热词有用，本质就是"让结果里出现正确的词"。
2. **注入 LLM 提示词**（`anchors` + `terms`）：让选片与起标题的模型知道这些词**是对的、不要改写**。
   不注入的话，模型会把「闪身步」自作聪明"纠正"成「闪身部」，把对的改错。

术语表存在 `data/glossary.json`（**独立文件**，不是 config.json：它是内容不是设置，
可以直接用记事本编辑，保存即生效，改坏了也不会影响服务配置）：

```json
{
  "anchors": ["甲主播"],
  "terms": ["后半夜后悔时代", "闪身步"],
  "replacements": [
    { "from": "闪身部", "to": "闪身步" },
    { "from": "\\d+次红包", "to": "很多次红包", "regex": true }
  ]
}
```

界面上在 **设置 → 字幕与术语表** 里编辑（一行一个），并提供「复制热词」两个按钮：
将来换成本地 whisper（`initial_prompt`）或云厂商控制台的「定制热词」时可以直接粘贴。

> 关键性质：**改术语表不需要重新转写**。纠错发生在 ASR 之后、落盘之前，
> ASR 缓存里始终保留原始输出，所以调术语表是零成本的。

验证：

```powershell
node test/subtitle-glossary.ts        # 55 项：ASS 时间戳/折行/合并/纠错规则（无网络零费用）
node tools/subtitle-burn-check.ts     # 真实素材：真切片一条并抽帧，人眼确认字幕与弹幕共存
node tools/glossary-api-check.ts      # 术语表接口：中文存取、坏正则被拒
```

## 投稿标题检测与投稿体检

### 为什么需要

实测踩到过一场直播的切片被投了 **3 次**（20:47–20:58 五次单投 → 21:17 一次 6 分P → 22:11 又一次 6 分P），
而且最后一次反查到的 bvid 是**完整版录播**的 —— 因为多分P 稿件的主标题
（`{直播标题} {日期}`）与完整版录播的标题**逐字相同**，按标题反查必然撞车。
这些在界面上完全看不出来：任务卡只显示「已发布 N」。所以做了两道检测。

### 一、投稿前标题体检（`src/title-check.ts`）

原来只查「长度 ≤80」，会漏掉这些：

| 级别 | 检查项 |
|---|---|
| **必须修** | 空标题、占位标题（`（待填写）`/`待补`/`示例标题`）、含换行、纯符号、≤2 字符、**术语表错词残留** |
| 建议看 | 超 80 字符会被截断（含「加后缀之后才超长」）、疑似哈希/文件名残渣、内部编号（`片段3`/`clip_12`）、分P 前缀（`P3 xxx`）混进单片标题、与同场其它切片重名、连续空格、≤6 字符 |

**术语表错词残留**是这里最有价值的一项：`data/glossary.json` 里配的纠错规则，
如果那个错词最终出现在标题里，说明模型把专有名词改写了 —— 这种稿子发出去观众一眼看出是机切的。

调用点：
- `POST /api/task/:id/approve`（半自动发布）→ **error 级直接拦下**，返回问题清单；
- 多分P 投稿（`publishAsMultiPart`）→ 主标题与每个分P标题都过一遍，**只告警不阻断**
  （一次投出全部，因为一条标题不合格而整体不投代价更大）。

### 二、bvid 反查错配检测（`verifyArchiveMatch`）

`/bili/upload` 只返回 taskId，bvid 只能靠 `GET /bili/archives` 按标题反查。
但**命中不等于正确**。写入 bvid 之前现在必须过三道闸：

1. 必须是**精确匹配**（归一化后完全相等），包含匹配一律不认；
2. 稿件的创建时间必须晚于本次提交（`ctime` **缺失时也拒绝** —— 实测正是这种情形把完整版 bvid 写了进去）；
3. 命中标题不能是该场的**完整版录播标题**（多分P 主标题与它天然相同）。

任一不通过 → 拒绝写入 bvid，切片保持 `SUBMITTED`，日志与投稿流水里都留一条说明。
多分P 幂等反查同样会排除完整版，并在"命中了但都不可信"时**明确打警告而不是静默跳过**。

### 三、投稿体检（界面上随时能跑）

任务详情页「投稿体检」按钮，或：

```powershell
node tools/publish-audit.ts <taskId>            # 本地分析，瞬间出结果
node tools/publish-audit.ts <taskId> --remote   # 额外核对 B站 侧可见性
```

报告内容：

| 区块 | 说明 |
|---|---|
| 结论 | `正常` / `需核对` / `不合格` + 可执行建议 |
| 投稿批次 | 本场每一次投稿（按 uploadTaskId 归组）：时间、单片还是 N 个分P、用了哪些标题、反查到哪个 bvid |
| 重复投稿 | 同一个切片被投了几次、每次的标题 |
| bvid 可信度 | 共享 bvid、**指向完整版录播的批次**（这类台账 bvid 不可信） |
| 标题逐条 | 每条标题的 error/warn、以及"提交时会变成什么样"（截断后） |
| 线上可见性 | 「定时发布未到点」的稿件在 B站 侧查不到详情，显示不可见是正常的 |

> 体检**只读**：不改任何状态、不提交任何东西。线上稿件的删除/修改只能去 B站 创作中心。

### 四、分P 标题模板（`publish.partTitleTemplate`）

切片分P 标题原来是硬编码的 `P{n} {title}`，创作中心里看到的就是「P3 主播收到飞机礼物…」。
现在可配置，留空则沿用旧行为：

| 变量 | 含义 |
|---|---|
| `{n}` | 分P 序号 |
| `{title}` | 切片自己的标题 |
| `{mainTitle}` | 稿件主标题 |
| `{anchor}` | 主播名（从历史稿件标题推断） |
| `{date}` | 录制日期 |
| `{kind}` | 类型（切片/完整版/纯享版） |

例：`{anchor}切片{n} {title}` → `甲主播切片3 有人中了20次红包？主播直呼搞不懂`。
设置面板里**边敲边看预览**，未知变量会原样保留并提示拼写问题。

验证：

```powershell
npm run title-test                    # 45 项：标题体检 / bvid 校验 / 批次分析 / 标题模板（无网络）
node tools/publish-audit.ts <taskId>  # 对真实场次跑一次体检
```

### 五、续传：切片追加进 biliLive-tools 的**同一个稿件**

用户的工作流是「一场直播 = 一个稿件」：biliLive-tools 负责录制 + 把分段录播投成稿件的分P，
切片助手只把切片**追加**进那个稿件。

**biliLive-tools 侧的行为（读它的 `app.asar` 源码 + 实测账号稿件确认，不是推测）**：

- `Live` 模型：`partMergeMinute`（当前 10 分钟）内接着录的分段算**同一场**的 parts（`Live.addPart`）；
- `uploadNoDanmu && uploadToSameMedia`（两项当前都已开）时走 `uploadVideoToSameMedia()`：
  已有 `live.aid` 就 `editMedia`（append 追加分P），没有就新建稿件并记下 aid；
- 实测结果：一场 6 小时的直播 → `BV13hhE6XEQM` **14 个分P**（P1–P7 弹幕版分段 + P8–P14 纯享版分段）；
  另一场 `BV1sqhq6hEZ2` 10 个分P、`BV1Abh66eEuh` 4 个。

**我们这侧**：

1. **只分析一次**：触发器按 `live_id` 聚合（`groupByLiveId`），同一场的多个分段文件进**同一个任务**，
   转写/分析/切片各跑一遍，不是每段跑一遍。实测录制历史里最多一场有 14 个文件共享一个 `live_id`。
2. **追加切片**：`publish.resumeAid`（显式 aid）或 `publish.resumeTitleTemplate`（自动找）→
   `POST /bili/upload` 带 `vid` → biliLive-tools 走 `editMedia`，`append` 模式
   **保留原分P、只加新的**，且它会把稿件原有的标题/简介/标签原样 POST 回去
   （源码 `{...archiveData, ...{aid}}`）—— 我们的投稿 config 覆盖不到稿件信息。
3. **分P 编号基准自动对齐**：读目标稿件的实际分P 数（`biliArchiveDetail` → `View.pages`），
   所以 14 个分P 的稿件里追加的第一个切片标题是 `P15 …`，不会出现「标题写 P1、实际挂在第 15 个分P」。

**自动找稿件的两条路**（`resolveResumeTarget`）：

| 轮次 | 比较方式 | 额外要求 |
|---|---|---|
| ① | 连日期一起精确相等（`{anchor}{liveTitle}{date}`） | —— |
| ② | 只比「主播名 + 直播标题」（日期差一天也能命中：跨零点 / 手动导入） | 目标稿件必须有 `ctime`，且落在录制日 ±7 天内 |

任何一轮命中**多于 1 个**都拒绝自动选择（宁可新建稿件，也不把切片挂到别的稿件的分P 里）。

`{anchor}` 的取值顺序：**先从稿件列表反推账号名**（`guessAnchorName`，标题形如
`甲主播<直播标题>2026.09.22`），再用台账里识别到的主播名兜底。
这一步是必须的 —— biliLive-tools 的标题模板是 `{{user}}{{title}}{{now}}`，开头就是账号名；
早期实现把 `{anchor}` 渲染成空串，实测精确命中 **0** 个，于是每次都新建稿件。

验证：

```powershell

node tools/resume-target-probe.ts     # 用**真实稿件列表 + 真实台账**跑一遍解析，给出行不行
node tools/archive-parts-probe.ts <bvid>   # 看某个稿件的真实分P 列表

# 预演一次「追加进那个稿件」：只检查素材/额度/分P 编号，不投稿
node tools/publish-multipart.ts <taskId> --aid <稿件aid> --dry-run
# 真投（会往那个稿件加分P，不可撤销）：去掉 --dry-run；--no-resume 则强制新建稿件
```

### 六、完整版归谁投：**默认 biliLive-tools，例外才由切片助手**

这是一条**规则**（用户定的），不是实现细节：

| 情况 | 完整版（弹幕版 + 纯享版） | 切片 | 稿件结构 |
|---|---|---|---|
| **默认** | **biliLive-tools 投**（它压制 + `uploadToSameMedia`） | 切片助手只追加切片分P（`vid` → `editMedia`） | 一场 = **一个稿件**：它的 2Z 个分P（Z = 分段数）+ 我们的 N 个切片 |
| **例外**（只有明确说明时） | **切片助手投**：自己烧弹幕版 + remux 纯享版 | 切片助手投 | 新建 **2+N** 稿件：P1 完整版 · P2 纯享版 · P3… 切片 |

**默认路径下的等待行为**（关键）：biliLive-tools 的压制 + 上传是异步的（实测录制结束后 13–15 分钟才出弹幕版），
而我们切片完成得更早。这时**不允许自己上**（自己投 P1/P2 会变成同内容两个稿件），
也**不允许**把切片投成独立稿件（违背"同一个稿件"）：

- 本场停在 **已切片**，台账写 `publishWait`（起始/截止/原因），界面任务卡显示 **⏳ 等完整版稿件**；
- 等待循环每 5 分钟重查一次它的稿件，一出现就**自动追加切片分P**并清掉标记；
- 超过 `publish.resumeWaitMin`（默认 90 分钟）仍没等到 → 停在「已切片」并告警，
  提示去确认 biliLive-tools 侧（房间有没有压制预设 `ffmpegPreset`/`danmuPreset`、这场是不是它自己录的、它那边有没有报错）。

**怎么"明确说明"由切片助手投**（三选一，任务级优先）：

| 方式 | 写法 | 作用范围 |
|---|---|---|
| 界面（推荐） | 打开某场 →「本场设置 → 完整版由切片助手投（例外）」→ 保存 | 只这一场 |
| 界面（全局） | 设置 → 发布策略 →「完整版（弹幕版 + 纯享版）由谁投稿」 | 之后所有场次 |
| 手工工具 | `node tools/publish-multipart.ts <taskId> --as-assistant` | 只这一次命令 |

护栏：
- `multiPart=false` + 默认规则（完整版归 biliLive-tools）会被**配置校验直接判错** ——
  单切片一稿模式下每个切片是独立稿件，天生满足不了"同一场 = 同一个稿件"；
- 全局切到 `assistant` 会给出「这是例外」的告警。

验证：`npm run multipart-routing-test`（43 项：等待行为 / 例外生效 / 等到了自动追加 / 配置护栏）、
`npm run ui-e2e`（88 项，含"打开例外开关 → 保存 → 台账真的记下 `overrides.fullVideoBy`"的往返）。

## 导入录播（参考 biliLive-tools）

### 为什么改

原来是「粘贴一个视频文件的绝对路径」。实测这条路有三个坑：

1. 用户得自己去资源管理器复制路径，还容易复制错；
2. 同一次录制会产出 **3–5 个文件**（原始 `.flv`、`-弹幕版.mp4`、`_PART000.flv`…），逐行列出来根本分不清该选哪个，
   而且**错选 `-弹幕版` 就会烧出双层弹幕**（画面里已经烧过一次了）；
3. 弹幕要自己找同名文件，文件名对不上就找不到，导错了要等流水线跑失败才发现。

### 文件名的真实形态（2026-09-24 实测，比文档里写的更花）

一场连续直播在盘上留下的名字，实测长这样：

```
2026-09-24 00-48-58-767 哈喽.ts                                   ← 原始录制（第 1 段，209 秒）
2026-09-24 00-48-58-767 哈喽-弹幕版.mp4                            ← 压制产物
2026-09-24 00-48-58-767 哈喽-弹幕版-6e88e7c6-1c78-4827-917b-….mp4  ← 二次压制的产物（带防覆盖 UUID）
2026-09-24 00-52-25-165 哈喽.ts                                   ← 第 2 段（561 秒，首尾相接）
2026-09-24 01-01-56-910 哈喽-PART000.ts                           ← 第 3 段（**连字符**分段）
```

| 形态 | 它是什么 | 不认它会怎样 |
|---|---|---|
| `-弹幕版-<uuid>` | biliLive-tools 的 `burn()` 发现同名产物已存在时，用 `uuid()` 改名后的结果 | ① 归成**另一场**→ 同一段素材被导入两次（转写/分析各花一遍钱，还各投一次稿）；② 判成"没烧过弹幕"→ 再烧一层就是双层弹幕 |
| `-PART000`（连字符） | 同一场直播被按分钟切段时的分段名（老形态是 `_PART000`） | 标题残留成 `哈喽-PART000` → 拿去匹配稿件匹配不上 → **另投一个新稿件**（本该追加分P） |

两条都在 `test/recordings.ts` 里有回归用例（4d / 4e），`discoverSegments` 的匹配器还修了
「认得出分段形态、却匹配不上分段文件」的漏洞（漏了前缀后的分隔符 + 少了 `i` 标志）。

### 同一场只导一次

判重不只看"这个文件导过没有"，而是看**这一场导过没有**：

- 先按首选源文件（未烧弹幕的那个）的路径比台账；
- 再按同组其它变体比（实测事故：原始 `.ts` 投稿完被清理删掉、盘上只剩弹幕版产物，
  只按首选文件判重就会把同一段素材再导一次）；
- 最后按**场的归并键**（目录 + 去后缀文件名）比台账兜底。

biliLive-tools 好用的地方在于它有三样我们原来没用上的东西，现在都用上了：

| 它的能力 | 接口 / 配置 | 我们怎么用 |
|---|---|---|
| 录制历史（带标题、开播时间、时长） | `GET /record-history/list` | 清单里标题与房间号以它为准，比从文件名猜可靠；**逐个查它自己在录的所有房间**（`virtualRecord.config[].roomId`），否则别的主播的历史进不来 |
| 「视频 ↔ 弹幕」对应关系 | `POST /record-history/danma-file` | 选中文件时问它一次，比"找同名文件"准（改过名、换过目录也能找到） |
| 它自己的保存目录 | `GET /config` → **`recorder.savePath`** | 自动加进扫描目录。实测它是 `~/Downloads`，B站录播在 `Downloads\Bilibili\<主播>`、抖音录播在 `Downloads\抖音\<主播>` |

> ⚠️ 这里踩过一个坑：一开始只找 `webhook.recoderFolder`，而实测字段名是 `recorder.savePath`，
> 于是**永远探测不到**，扫描范围静默退化成硬编码的 `~/Downloads/Bilibili` ——
> 用户放在 `Downloads\抖音\主播杨树` 的录播完全看不见（用户实际反馈："路径太绝对了，我还有别的主播的录播没显示"）。
> 现在按「任意前缀 + `recorder.savePath` / `video.subSavePath` / `tool.download.savePath` / 老字段」匹配，并把找到的**全部**目录都用上。

### 扫描范围：可看、可改

导入对话框顶部有「扫描目录（录播没显示出来？在这里加）」：

- **自动**：biliLive-tools 的保存目录（不需要手填，也不能删）
- **手动**：`import.scanDirs` 里你自己加的目录，界面上可加可删（支持 `~` 开头，回车即加）
- 下面还会列出**本次实际扫描了哪些目录**、以及**录制历史查了哪几个房间、共多少条、其中多少条的文件已不在磁盘**

同一台机器上不同平台/不同主播的录播放在不同目录时，把那些父目录加进来即可。
扫描时会**跳过** `$RECYCLE.BIN`、`System Volume Information`、`node_modules`、`Windows` 等目录
（实测放宽扫描根之后，回收站里的文件也被列出来了，非常困惑）。

### 现在的导入流程

```
打开「导入录播」→ 列出可导入的录播（按"场"归并）→ 点一行
   → 自动带出：视频路径、配对的弹幕、标题（可改）
   → 预览：时长 / 大小 / 分辨率 / 分段数 / 弹幕来源 / ASR 预估费用 / 是否已导入 / 是否仍在录制
   → 确认导入
```

清单里每条都标出关键状态，每一条都对应一个实测踩过的坑：

| 标记 | 含义 |
|---|---|
| **可能仍在录制** | 文件刚被写入过（默认 120 秒内）。现在导入会拿到半场素材 |
| **已导入** | 该文件已属于某个任务，再导会新建一场并**重新花 ASR 钱** |
| **画面已烧弹幕** | 选的是 `-弹幕版` 压制产物 → 导入时会写 `fullVideoHasDanmaku=true`，切片不再叠 ASS（陷阱 #8） |
| **文件不可用** | 录制中断的 MP4 没有 moov atom，ffprobe 读不出时长（导入前就拦下，不用等流水线报错） |
| **N 个版本** | 同一场的原始 / 压制 / 分段文件，界面里可一键切换源 |

扫描目录：`import.scanDirs`（配置，支持 `~`）+ biliLive-tools 的保存目录（`recorder.savePath`）+ `~/Downloads/Bilibili`。
递归深度 `import.maxDepth`、忽略小于 `import.minSizeMB` 的文件。界面上的「扫描目录」里可加可删。

清单接口有 20 秒缓存（扫盘要对每个文件跑 ffprobe），界面上的「刷新清单」按钮传 `refresh=1` 绕过。

验证：

```powershell
npm run recordings-test              # 96 项：文件名解析（含防覆盖 UUID / `-PART000`）/ 同场归并 / 多分段合并 / 判重 / 弹幕配对 / 预览警告（无网络）
```

## 实时监控面板（守着直播时看的那一页）

界面第二个页签「**实时监控**」，默认 **5 秒**自动刷新（可切 3 / 5 / 10 / 30 秒，或暂停）。
它回答的是守着直播时真正会问的四个问题，而不是"依赖是否正常"（那是「健康面板」的活）：

| 块 | 回答的问题 | 数据来源 |
|---|---|---|
| **状态灯**（8 个 KPI） | biliLive-tools 连没连上、B站账号还剩几天、磁盘够不够、队列忙不忙、今天投了几条、今天花了多少钱、待删多少、近 24h 有没有错误 | `/api/monitor` 聚合（内含 `orch.health()`） |
| **流水线** | 现在在干什么：每一场的 5 段阶段条（录制 › 转写 › 分析 › 切片 › 发布）、转写进度 `12/24`、已用多久、花了多少、是否在等完整稿件 | 台账 + `summarizeTask` |
| **在等什么** | 哪些场在等 biliLive-tools 投出完整版（含原因、剩余时间、已试次数）、哪些切片已排期待投、哪些文件待删及到期时间 | `publishWait` / 切片 `dtime` / `pending-delete.json` |
| **目录轮询** | **某个录播为什么没被导入**：在盯哪些目录、上次扫描多久前、正在录制的文件、以及上一轮对每个文件的结论（已导入 / 正在录制等写完 / 历史积压 / 失败退避） | `WatchImporter.status()` |
| **biliLive-tools 队列** | 它现在在压制/上传什么（完整版的弹幕版与纯享版） | 它的 `GET /task/`（**1.5 秒超时 + 缓存 10 秒**，绝不拖住面板） |
| **最近投稿 / 最近错误** | 刚投出去的切片与 bvid（可直接点开），以及最近错误事件（可一键看脱敏报告） | 台账 + `errors.jsonl` |

几个刻意的设计：

- **一个接口给全**（`GET /api/monitor`），不是让页面并发打 6 个接口 —— 否则各块时间点不一致，
  会出现"队列空闲"和"正在转写"同屏这种自相矛盾的画面。
- **每一块独立降级**：某一跳超时（例如 biliLive-tools 正忙）只让那一块显示提示，
  **绝不整页空白** —— 监控面板最忌讳的就是"因为一个依赖挂了而看起来像助手死了"。
- **数据没变就不重画**：5 秒一次的 `innerHTML` 重画会把页面变成闪烁的幻灯片，
  所以先比"去掉易变字段后的指纹"，没变就只更新「最后更新」那一行。
  指纹要去掉的字段是**实测**出来的（连比两次快照）：`now`（时间戳）、
  `uptimeSec` / `elapsedSec` / `remainSec`（每跳都变）、`freeBytes`（每写一行日志就动）、
  以及按显示精度比的 `freeGB` / `daysLeft` —— 漏掉任何一个都会"永远判定为变了"。
- **切走页签就停表**：没人看的时候不必每 5 秒问一次服务端。
- **1.2 秒短缓存**：吸收"多标签页 + 手点刷新"的重复请求，同时保证面板不会显示过期状态。

```powershell
npm run monitor-panel-test           # 58 项：页面接线（页签/定时器/构建号/脚本可解析）+ /api/monitor 数据契约 + 缓存语义
npm run ui-e2e                       # 真浏览器：点开页签、断言六块渲染、验证自动刷新真在跑、数据没变时不重画
```

## 回收站：删除不再不可逆

### 为什么加

**这是一次真实事故**：通过界面点「删除任务」后，服务日志显示

```
已删除切片产物：data\clips\manual-20260922121832-zdd2（释放 222.8 MB）
已从台账删除任务 manual-20260922121832-zdd2（释放 6 条幂等指纹）
```

—— 222.8 MB 成片 + 任务目录（转写/信号/总结）+ 台账记录一起被**永久**删除（实现是 `fs.rmSync`），
事后除了一行日志没有任何恢复依据。对"点错一下"这种最常见的失误，代价完全不成比例。

### 现在的行为

删除 = **移入回收站**（同盘 `rename`，瞬时、不复制字节）：

| 位置 | 内容 |
|---|---|
| `data/trash/<时间>-<taskId>/` | 被删的文件与目录（按原样保存） |
| `data/trash/<时间>-<taskId>/manifest.json` | 被删任务的**完整台账快照** + 每个文件的原始绝对路径 |
| `data/ledger-backup/<时间>-<taskId>.json` | 删除前的整份台账（保留最近 20 份） |

- **恢复**：设置 → 回收站 → 「恢复」，会把文件搬回原位**并把台账记录写回**（所以任务能继续用）。
  目标目录已被台账重建时按项**合并**，不覆盖已存在的同名文件。
- **彻底删除**：只有「清空回收站」会真正 `rmSync`，且需要二次确认。
- **自动清理**：`cleanup.trashDays`（默认 7 天），由每日的稿件表现回流任务顺带清理；设为 `0` 表示关闭回收站。

界面上删除成功的提示会明确告诉你是「已移入回收站（可恢复）」还是「已删除」，
接口返回里的 `trashId` 就是判断依据。

> ⚠️ 这里修过一个"看起来删了其实没删"的缺陷：勾选「任务目录」后目录**原地还在**（空的）。
> 根因是删除流程里一个只读动作会**顺手把目录建回来** —— `ledger.deleteTask()` 要读 `clips.json`，
> 而取路径的 `taskFile()` 走的是 `taskDir()`，那个函数里有 `ensureDir`。
> 记录里带 `clipsPath` 时不走这条路（所以单元测试一直是绿的），真实的场次没有这个字段，
> 于是出现"回收站里有条目、`data/tasks/<id>` 却还在"。
> 现在只读路径一律走不创建的 `taskDirPath()` / `taskFileReadonly()`，
> 删除后再兜一层：**只在目录为空时**移除残留。回归用例见 `npm run delete-test` 场景 4。

验证：

```powershell
npm run trash-test                   # 26 项：移入 / 恢复（含台账）/ 冲突处理 / 清空 / 健壮性（无网络）
npm run delete-test                  # 15 项：只删切片保留记录 / 勾任务目录整体删除 / **删除后目录不得残留**
```

## 关键设计取舍（为什么这么做）

| 决策 | 原因 |
|---|---|
| **不 fork biliLive-tools** | fork 需构建 Electron + pnpm monorepo 并持续跟随上游更新，且 GPLv3 分发有义务；调用 HTTP API 无此负担 |
| **不自己写 ffmpeg 命令** | 切割、烧弹幕、时间戳处理、上传协议全部由基础设施层承担，自研层只做「决策 + 调度」 |
| **完整版上传与转写并行** | 上传吃带宽、转写吃算力，互不冲突。先等上传完成再转写会把出片时间从 1.5–3.5 小时变成 3–5 小时 |
| **切片不等完整版上传** | 切片的前置条件只有一条：源文件存在且可用。台账记录上传状态的唯一用途是判断「源 mp4 何时可以删」 |
| **删除权归本服务** | biliLive-tools 的「上传后删除」会在稿件过审后删源文件，而它过审可能只要几分钟、转写要 20–40 分钟，会形成竞态；且它走内部引用计数，外部无法为文件加锁 |
| **轮询始终保留** | `recent-clips` 只返回 5 条，跨场次会漏；`/webhook/*` 是**入站接口**，自研服务不能从那里订阅事件。轮询是可靠兜底 |
| **下播确认** | 直播中途断流时第一段也会满足「有新 id + 有结束时间 + 文件大小稳定」。不叠加下播确认就会对半场素材转写+分析，恢复后又触发一次 |
| **契约校验失败升级模型重跑** | 让同一个便宜模型原地重试，失败率不会明显下降。评测显示「JSON 格式通过率 99.97%」的模型，内容完全正确的比例可能只有 0.486 |
| **转写本地缓存** | `/ai/subtitle` 在源码中硬编码 `disableCache: true`，每次调用都是真实 ASR 请求，**重复调试重复计费** |
| **缓存键不用 `videoFileId`** | 它来自 biliLive-tools 内存中的 fileCache（24 小时过期、进程重启即清空），重启后同一文件会拿到新 id，导致缓存全部失效 |
| **幂等指纹只存本地** | `dynamic` / `desc` 都是公开可见的，把指纹写进去观众会看到一串无意义字符 |
| **bvid 靠 `GET /bili/archives` 反查** | `/bili/upload` 只返回 `taskId`，而任务队列在内存中、进程重启即丢 |
| **UI 单文件、只监听 127.0.0.1** | 环境无 Python、不应引入构建链；且上传接口会读本地文件路径，绝不能暴露公网 |

## 常见故障排查

### ① 一直不触发（recent-clips 返回空数组）

这是**最隐蔽**的故障：接口不报错，只静默返回 `[]`。两个原因：

1. **`platform` 传错** —— 必须是 `Bilibili`（首字母大写），不是 `bilibili`。
2. **该直播间在 `streamer` 表中没有记录** —— 即从未录制过。先在 biliLive-tools 里为它添加录制任务并至少完成一次录制。

诊断：`node src/cli.ts selfcheck` 会明确告诉你是哪种原因。

### ② 401 鉴权失败

`config.json` 的 `bililive.passKey` 与 biliLive-tools「设置 → 服务」中的 PassKey 不一致。
也可以在启动前设置环境变量：`$env:LIVE_AUTO_BILILIVE_PASSKEY = "..."`。

### ③ B站 cookie 过期（**唯一无法自动解决的情况**）

症状：上传失败、`/user/list` 的 `expires` 已过、UI 健康面板红色告警。

处理：在 biliLive-tools 中**重新扫码登录**。本服务每日检查有效期，临近过期（默认 7 天）会提前告警。

### ④ 转写报错「请先在配置中设置字幕识别ASR模型」

到 biliLive-tools → 设置 → AI 配置 → 模型，为「字幕识别」指定一个**勾选了 ASR 标签**的模型。

### ⑤ 切片报「输入文件不存在」/ 转写读到不存在的文件

**检查 biliLive-tools 的「上传后删除素材」是否已关闭**（`afterUploadDeletAction` 必须为 `none`）。
它开启时会在稿件过审后删掉源视频，导致后续转写与切片失败——而且故障表现分散（一边转写报错、一边切片报文件不存在），看起来像两个不相关的 bug。

`node src/cli.ts selfcheck` 会检查这一项并给出修复步骤。

### ⑥ 切片画面出现两层弹幕

说明源文件（完整版）已经烧过弹幕，切片时又传了 `assFilePath`。

处理：如果压制环节已经把弹幕烧进完整版，把 `clip.fullVideoHasDanmaku` 设为 `true` ——
此时切片直接从完整版切且**不传 ASS**（画面里的弹幕本身就是正确的）。

### ⑦ 切片开头花屏 / 弹幕整体错位

说明用了 stream copy。切片**必须重编码**，两个独立原因：
① stream copy 只能切关键帧，开头会花屏/黑帧；
② `-copyts`（弹幕对齐机制）只在重编码时添加。

本项目的 `api.ts` 会在客户端直接拒绝 `c:v=copy`。

### ⑦b 字幕和声音对不上（已修，含实测数据）

**症状**：观众先听到词，过 1–4 秒才看到对应画面与字幕（弹幕同理）。

**根因不在字幕生成，而在切片产物的音视频时间轴**：录播 `.ts` 的 PTS 结构使视频流比音频流靠后，
切出来的成片里两条流的起点不一致。实测：

| 检查项 | 结果 |
| --- | --- |
| 源录播两条流起点 | 都是 1.433（同步） |
| 切片产物 | 视频 4.800 / 音频 1.239 → **音频早 3.561 秒** |
| 用 `-c copy` 原样搬运 | 同样 3.560 秒 → 不是 ffmpeg 参数问题 |
| 起点对齐关键帧 | 仍 2.755 秒 → 也不是关键帧吸附问题 |
| 16 个历史成片 | **7 个错位 >0.5 秒，最大 3.742 秒** |

**修法**：切完片后自动重挂一次（`src/av-sync.ts`），把起点靠前的那条流整体后移，使两条流起点一致。
纯流拷贝：不重编码、不损画质、画面与已烧好的字幕一个像素都不动，80 MB 约 0.1 秒。
配置项 `clip.avSyncRepair`（默认开）、`clip.avSyncToleranceSec`（默认 0.15 秒）。

**查历史成片**：`node tools/av-sync-repair.ts`（只报告）/ `--apply`（真的修）。
注意 B站上已投稿的视频不会被改动，要自己决定是否删掉重投。

**定位工具**（排查同类问题时按这个顺序用）：

1. `node tools/av-sync-audit.ts` —— 扫所有成片的音视频起点差，一次看出是不是系统性问题；
2. `node tools/audio-align.ts <源> <成片> <源起点> <成片起点> <窗长>` —— 音频包络互相关，
   测出"成片某一刻的声音实际来自源的第几秒"。画面内容则用**录播自带的墙上时钟**定标
   （裁左上角时钟区域抽帧，与源同位置的时钟一比即可，无需 OCR 之外的任何东西）；
   两条流的定标一比，就能算出"字幕/画面 与 声音"到底差多少 —— 这是唯一无法自欺的测法；
3. `node tools/clip-subtitle-verify.ts <taskId> <clipIndex>` —— 从**已投稿的成片**抽帧，
   列出该时刻"应当显示的字幕"，肉眼比对；
4. `node tools/subtitle-preview.ts <taskId>` —— 内存里预演字幕生成效果（条数/时长/断句/折行）+
   核对磁盘上生产 ASS 成品；
5. `node tools/subtitle-burn-check.ts <taskId>` —— 真切片 + 真烧录 + 抽帧（不投稿）。

**已知残留**：切片起点会被关键帧吸附推后 0–4.2 秒（关键帧间隔 4.17 秒），
因此成片的实际内容比"请求的起点"晚几秒开始 —— 字幕与画面、声音三者仍然互相同步，
但**开头可能少掉几秒**。若要连开头几秒一起保住，把请求的起点提前一个关键帧周期即可（待办，未实现）。

### ⑧ 投稿被拒（定时发布时间）

`dtime` 必须**晚于该稿件自身的提交时间 7200 秒**。默认公式 `submitTime + 7800 + (N-1)×7500 + random(0, 1800)` 已留足余量。

> 注意：B站的硬限制是「相对**该稿件自己的提交时刻** > 7200 秒」，**相邻切片的间隔不受额外限制**。
> 取 7500 只是保守余量，不是「相邻差正好 7200 就会被拒」。

### ⑨ 切片没有归入同一合集

`/bili/upload` 接受 `seasonId` / `sectionId`，但**没有任何接口能创建合集**。
需要在 B站创作中心手动建一个合集，把 ID 填进 `config.json` 的 `publish.seasonId`。留空时切片照常投稿但不会归入合集。

### ⑩ 磁盘空间不足

默认剩余低于 **50 GB** 时停止新任务并告警。

```powershell
node src/cli.ts clean --dry-run   # 先看会删什么
node src/cli.ts clean             # 实际执行
node src/cli.ts health            # 查看素材占用与可清理量
```

分层清理策略：
- **原始分段（flv/ts）**：压制产物校验通过 **且** 转写完成后才删（它们体积最大，一场 4 小时可达十几 GB）
- **压制后的 mp4**：该场**全部切片上传完成 + 完整版上传完成**后，再等缓冲期（默认 7 天）才删

### ⑪ 想省钱

**ASR 是主要运行成本**（一场 4 小时约 ¥6–10，一个月 30 场约 ¥180–300）。LLM 成本几乎可以忽略（几分钱到两三毛）。

优先考虑：
1. **本地 Whisper 方案**（需要带 `whisper` 滤镜的 ffmpeg 与 ggml 模型）—— 这是把每月两三百降到零的唯一途径
2. **本地剪静音**（`asr.silenceTrim.enabled = true`）—— 直播中纯游戏操作、长时间不说话的段落占比很高，通常能省 **20–40%**

```powershell
# 检查手上的 ffmpeg 是否带 whisper 滤镜
ffmpeg -hide_banner -filters | Select-String whisper
```

### ⑫ 出错了怎么查

```powershell
node src/cli.ts inspect                  # 列出最近错误
node src/cli.ts inspect <taskId>         # 打印完整报告
```

报告包含：上下文（任务、失败阶段、版本）、错误本体（类型/消息/堆栈）、**脱敏后**的请求参数与响应体（>4KB 截断并记录原始长度）、重试历史、**biliLive-tools 侧日志片段**（切片/压制失败的真因通常在那里）、环境快照。
报告中不会有任何未脱敏凭据——`test/redact-selftest.ts` 有 76 项断言守着这条线。

Web UI 的失败态也提供「查看日志」（渲染后的错误时间线，可一键复制）与「从该阶段重跑」。

## 全自动流程：把录播丢进目录就跑

打开助手之后不需要任何操作：**盯目录 → 自动导入 → 转写 → 总结选片 → 切片 → 投稿 → 用完即删**。

### 目录轮询导入（`import.watch`）

`src/watch-import.ts`，默认每 60 秒扫一次 `import.watch.dirs`（支持 `~`，递归 `maxDepth` 层）。

它与 `trigger`（轮 biliLive-tools 的 `recent-clips` 接口）是**两条独立的腿**：实测 `recent-clips`
会返回空数组（房间不在 biliLive-tools 的 streamer 表里时就是这样），而**盘上的文件是真实存在的** ——
盯目录是更可靠的兜底。

判定规则（每一条都对应一类真实事故）：

| 判定 | 原因 |
| --- | --- |
| **首次启用只登记基线、不导入** | 实测目录里已积压 28 个文件 / 32 GB，全导入等于一次排 28 场转写（≈¥238）并占满队列好几天。想处理积压请在界面手动导入，或设 `importExisting: true` |
| **mtime 早于「轮询启用时刻」→ 也算积压** | 基线快照的可信度取决于那次扫描范围是否正确。实测事故：扫描根曾经是空的（基线只登记了录制历史那 13 条），修好扫描范围后盘上所有老文件都被当成新录播 —— 所以再加一道与扫描范围无关的判据：`startedAt` + 文件修改时间 |
| **扫描范围变化 → 重新登记基线** | 加了新目录（或修好扫描范围）时，新范围里的老文件会被误判成新文件。此时重新登记基线并告警，而不是把整个新目录的积压导一遍 |
| 体积连续两轮不变且稳定 ≥ `stableSec` 才导 | 录制工具边录边写，导入正在写的 flv 会得到"看起来正常但内容不全"的任务 |
| `possiblyRecording` 跳过 | biliLive-tools 口径的最近写入窗口 |
| 台账 `importedBy` 跳过 | 同一文件绝不重复导入（重复导入 = 白花一次转写钱）。判重按**整场**：首选文件路径 → 同组其它变体 → 场的归并键（实测事故：`哈喽-弹幕版-<uuid>.mp4` 曾被当成另一场导进来，同一段 209 秒素材跑了两遍转写、两个任务，其中一条已经投出去了） |
| 失败退避 10 分钟 | 坏文件不该每 60 秒刷一条错误、反复建任务 |
| 只扫 `import.watch.dirs`、关掉 ffprobe 预检 | 轮询每 60 秒跑一次，扫描范围必须收敛。⚠️ `import.watch.dirs` 是通过 `listRecordingsDetailed` 的 `extraDirs` 传进去的 —— 那个字段曾经"声明了却没读"，导致扫描根为空、轮询退化成"只轮录制历史"（已修 + 回归用例） |

**任务来源要分得清**：自动导入与手动导入走的是**同一个 `importLocal()`**，早期它把 `manual: true`、
id 前缀 `manual-`、标题后缀「（手动导入）」全部写死，于是目录轮询自己捡起来的任务在界面上也显示「手动导入」。
现在任务带 `importSource`：

| 来源 | 界面标记 | 说明 |
| --- | --- | --- |
| `recording` | （无） | 轮询录制历史触发的正常直播场次 |
| `auto` | **自动导入** | 目录轮询自己捡起来的，标题不带人为后缀 |
| `manual` | 手动导入 | 界面「导入录播文件」/ CLI / MCP 建的 |

旧台账没有这个字段（那时自动导入也被写成 `manual: true`，无法回溯区分），界面按 `manual` 兜底显示「手动导入」。

**为什么会看到「在监控目录里的文件」却标着「手动导入」**：这两条路只差**谁先动手**。
轮询有刻意的安全延迟（mtime 120 秒内算"可能还在录" + 体积连续两轮不变 + 稳定 ≥ `stableSec`），
合计通常 **1–2 分钟**才导入；你在那之前从「导入录播」点了，记的就是**手动导入** —— 标记没错，
它回答的是"谁建的这个任务"。为了不再产生这种困惑：

- 导入清单里，落在 `import.watch.dirs` 内的文件会标 **在自动导入目录**；
- 选中后的预览会说明「不点导入的话轮询也会处理它，但要先等它写完」以及两种记账的区别；
- 右栏新增 **自动导入** 状态块：显示正在等哪些文件、扫描目录数、已自动导入数、以及多少个历史文件
  按配置不自动导入（`GET /api/watch` 的数据）。

界面：`GET /api/watch` 看状态与"每个候选为什么没导"，`POST /api/watch/scan` 立即扫一轮（设置页有入口）。

### 用完即删（`cleanup.deleteAfterUpload`）

用户要的是「上传完成后删掉切片和源文件」。删除源录播**不可逆**，所以做了三层保护：

1. **确认点必须硬**：只认 `PUBLISHED` + 经 `GET /bili/archives` 反查到 bvid（硬约束 #17）；
2. **本场全部切片都确认完**才排源文件 —— 任何一条还没确认就不动源，还能从源重切；
3. **进清单 ≠ 立刻删**：默认宽限 24 小时，界面上能看见"还有多久会删"并一键取消。

删法按盘符分流：成片在 `data/clips`（本盘）→ 移入回收站，可恢复 7 天；源录播在 `C:` 而回收站在 `F:`
（跨盘"移入回收站"要整份复制 20 GB，不现实）→ 到点直接永久删除，日志里写清删了什么、为什么可以删。

> ⚠️ 用这套就必须把 `cleanup.deleteRawAfterTranscribe` 设为 `false`：它会在**转写完成时**就删源，
> 比"上传确认"早得多，也是之前那次「找不到可用于切片的源文件」的直接原因。配置校验会在两者同时开启时告警。

界面：设置页「用完即删」按钮 → 待删清单（含已删除记录）→「取消删除」/「立即删除」/「全部立即删除」/「立即执行到点的删除」。
**实时监控**页的「在等什么」里也直接列出了待删文件，每行带「立即删除」（不用再翻设置页）。
接口：`GET /api/pending-delete`、`POST /api/pending-delete/cancel`、`POST /api/pending-delete/delete`、`POST /api/pending-delete/run`。

#### 「立即删除」：不想等宽限期的那条路

宽限期是"防手滑"的缓冲，但明确不要的文件还要等 24 小时纯属折磨（实测待删 15 项 / 472 MB），
所以给了显式入口 —— 同时把**两种截然不同的后果**在点下去之前就说清楚：

| 文件位置 | 删法 | 界面文案 |
|---|---|---|
| 与回收站同盘（`data/clips`、`media/` 下的产物） | 移入回收站 | 行内标「删除→回收站」；确认框写"7 天内可恢复" |
| 异盘（例如 `C:` 的源录播，回收站在 `F:`） | **永久删除**（跨盘搬 20 GB 不现实） | 行内标「跨盘·删除不可恢复」；确认框用"无法恢复"并**列出文件名** |

实现上的安全边界（每条都有理由）：

- 删法与**到点自动删完全共用**同一份 `performDelete()` —— 手动删不能变成绕过安全逻辑的野路子；
- 只接受**清单里的 id**，不接受调用方传路径（否则这个接口就是"删任意文件"的通道）；
- 已取消 / 已删过的条目直接跳过（用户的"反悔"不能被一次手滑覆盖）；
- 删除后记 `deletedManually: true`，与到点自动删区分开 —— 出"我的文件怎么没了"时能一眼分清是谁干的；
- 失败不抛异常：条目留在清单里带 `error`，界面能显示、可以重试。

## 本地转写：把 ASR 换成自己的机器（免费）

云端 fun-asr 按 ¥2/小时计费（一场 4 小时录播 ≈ ¥8.5）。`asr.provider` 支持三个引擎，
同一段 300 秒素材的实测对比：

| 指标 | 云端 fun-asr | 本地 faster-whisper | **本地 Fun-ASR-Nano** |
| --- | --- | --- | --- |
| 字错率 CER（对云端） | 基准 | 16.7% | **8.8%** |
| 时间戳偏差中位数 | — | −0.11s | **+0.18s**（p90 1.59s） |
| 推理 RTF | 0.032 | 0.036 | 0.168 |
| 4h15m 录播耗时 | 8.2 分钟 | 9.1 分钟 | **43 分钟** |
| 费用 | ¥8.5/场 | **0** | **0** |

### 用法

```powershell
# 1) 部署本地 Fun-ASR（独立 .venv-funasr，装 torch/funasr/modelscope，模型约 2 GB）
node tools/local-asr/setup-funasr.mjs

# 2) 切换引擎：界面「设置 → 转写引擎」，或 config.json 的 asr.provider = "local-funasr"
```

### 实现要点（每一条都是踩出来的）

- **整文件一次调用**：Fun-ASR 模型加载要 ~96 秒，按 30 分钟窗口切 9 段就白等 15 分钟。
  合并时必须**按文件分组** —— 多分段任务里每个文件只承载一部分全局时间，
  直接取第一个窗口拉成整场会让时间戳整体错位。
- **spec 的两套字段不能串**：`hub`/`timestamps`/`max_chars_per_cue` 只给 Fun-ASR，
  `compute_type`/`beam_size`/`model_dir` 只给 whisper；串了对面会报未知参数或静默走默认值。
- **stdout 只能放 JSON**：funasr 在 import 时打版本横幅、加载时打进度。runner 把库输出改道 stderr，
  调用方再兜一层"取最后一个带 `ok` 的 JSON 行"。
- **UTF-8 两层保险**（`PYTHONUTF8=1` + `reconfigure(encoding='utf-8')`）：Python 在 Windows 往管道写 stdout
  默认用 GBK，按 UTF-8 解码就是乱码**且不报错** —— 实测把 CER 算成 169%，看着像"模型完全不行"。
- **本地路径的 `paid` 必须是 false**：它决定"实际计费音频"的累计口径，
  写成 true 会让免费场次在成本统计里凭空多出 ¥8.5/场（被 `provider-e2e` 抓到）。
- 关掉 `asr.localFunasr.timestamps` 会退化成 VAD 段粒度，时间戳偏差从 ±0.2s 恶化到 ±2s。

工具：`compare-asr.ts --local both`（三方对比，`--ref` 复用已付费结果当基准）、
`provider-e2e.ts`（让流水线转写阶段真跑一遍本地引擎）、`setup-funasr.mjs`（一键部署）、
`download-torch.mjs`（可续传下载 torch）。

## MCP 接口：用对话驱动整条流水线

参考自 [Palmier Pro](https://github.com/palmier-io/palmier-pro) 的做法（应用打开时在
`127.0.0.1:19789/mcp` 暴露 MCP server，Claude Code / Codex / Cursor 一条命令接上）。
那款软件本身是 macOS 原生（Swift + Metal，仅 Apple Silicon），**我们无法本地部署**，
但"把已有 API 包成 MCP 让 Agent 直接操作"这一点非常值得抄 —— 而且我们的 API 面比它大得多。

服务启动后（首次启动会自动生成 token 并写回 `config.json`）：

```powershell
claude mcp add --transport http live-auto http://127.0.0.1:3000/mcp --header "Authorization: Bearer <token>"
codex  mcp add live-auto --url http://127.0.0.1:3000/mcp --header "Authorization: Bearer <token>"
```

token 与可直接复制的命令在界面上：**设置 → MCP 接口**。

### 能用它说什么

| 你说 | Agent 会调 |
| --- | --- |
| 「现在有什么任务在跑 / 哪场失败了？」 | `list_tasks` |
| 「`manual-xxx` 这场为什么没出片？」 | `get_task`（候选、失败原因、成本、总结） |
| 「把这场从 ANALYZED 重跑，只留弹幕峰值最高的 3 条」 | `retry_stage`（重跑选片） |
| 「我新录的那场怎么没导入？」 | `get_watch_status`（每个候选**为什么没导**） |
| 「现在扫一轮目录」 | `scan_watch_now` |
| 「取消删源录播」 | `list_pending_delete` → `cancel_pending_delete` |
| 「这场跑一次投稿体检」 | `publish_audit` |
| 「把腿宝、钢蹦加进术语表」 | `update_glossary` |
| 「第 2 条切片标题改成…，不勾选第 4 条」 | `edit_clip` |

共 **21 个工具**（只读 10 个）：任务 3、录播/轮询 3、清理 3、术语表 2、投稿体检与自检 2、
写操作 5（重跑/停止/导入/改切片/取消待删）、危险操作 3（删任务/预览删除/清空回收站）。

### 安全边界（三层）

1. **只监听 127.0.0.1 + 必须带 token**：MCP 客户端不是浏览器，拿不到页面的 CSRF token，
   所以单独发一个长期 token（`config.json` 的 `mcp.token`）。没 token 的本地进程不能驱动流水线。
2. **危险操作要一字不差的确认串**：`delete_task` 的 `confirm` 必须等于 `taskId`，
   `purge_trash` 必须等于「永久删除」—— 模型没法"顺手"删东西；确认串不对时**根本不会调用删除**。
3. **工具是已有逻辑的薄封装**：每个 handler 调的都是 REST 路由用的同一个 orchestrator 方法，
   不会出现"界面一套规则、Agent 走另一套"。

验证：`npm run mcp-test`（57 项，替身编排层，含确认串与 token 策略）、
`node tools/mcp-e2e.ts`（25 项，对着真实服务走完整流程）。

## 开源前的脱敏（要公开仓库就必做这一步）

`npm run audit` 只能证明**没有凭据泄露**（passKey / API Key / SendKey 都不在交付文件里），
它管不了**身份信息**：这个项目是照着自己的直播间写的，代码注释、文档、测试 fixture 里
天然带着真实房间号、常看的主播名、Windows 用户名、账号 uid 与昵称，两个弹幕 fixture 里
还留着**真实观众的弹幕正文**。私有仓库无所谓，**公开仓库等于把这些一起公开**。

```powershell
copy tools\sanitize-map.example.json .sanitize-map.json   # 首次：填真实值（该文件已被 gitignore）
node tools/sanitize-for-public.ts --dry-run    # 先看会改什么（不写盘）
node tools/sanitize-for-public.ts              # 真改（只动会被提交的那批文件）
node tools/sanitize-for-public.ts --check      # 复核：有漏网就退 1
```

映射表**放在 gitignore 的 `.sanitize-map.json` 里，不写在工具源码里** —— 表左边那列就是真名，
写死在源码里等于「脱敏工具把要藏的东西印在封面上」，而且看起来像已经处理过了，比不脱敏更危险。
仓库里只有模板 `tools/sanitize-map.example.json`。映射**顺序敏感**（长的、带后缀的先替换），
合成值刻意选得一眼看出是假的：`甲/乙/丙/丁主播`、`示例账号`、`demo`、`12345678`、`1000000000000000`。
两个弹幕 fixture 走特殊路径：**只把 `<d p="...">正文</d>` 的正文换成 `测试弹幕N`**，
时间戳/模式等属性一个字不动，所以结构、条数、断言全部照旧成立。
BOM 状态按文件原有情况保留（`.ps1` 必须带 BOM、其它禁止带）。

`--check` 不是简单的字符串查找，而是 **NFKC 归一化 + 去空白 + 转小写**三路比对 ——
真实稿件标题里出现过「全角字母 + 全角下划线」的写法，半角规则一条都不命中。

> **它绝不碰 `.gitignore` 里的运行期/凭据文件**（`config.json`、台账、日志、`data/`）。
> 这条不是洁癖，是踩过的坑：第一版把根目录 `config.json` 一起脱敏了，而那是**本机正在跑的配置** ——
> `room.roomId` 变成假房间号、`import.watch.dirs` 指向不存在的目录、`danmaku.factoryPath`
> 指向不存在的 DanmakuFactory.exe，守护进程还热加载了这份假配置（录制/自动导入/烧弹幕静默失效）。
> 脱敏的目标是「要提交的那批文件」，所以只跳过 `config.json` 这类**根目录**同名文件：
> `test/fixtures/config.json` 是真的要提交的 fixture，必须照常处理。

改完照例跑一遍 `npm run verify`（脱敏会改 fixture 里的断言数据，跑一遍才算数）。

## 安全须知

- 自研服务只监听 `127.0.0.1`，Web UI 带 Origin 校验 + CSRF token，预览接口仅限任务目录并防路径遍历。
- `config.json` 含凭据，已在 `.gitignore` 中。`.gitignore` 同时忽略 `data/`、所有日志、台账与决策流水。
- **要公开仓库**：先跑 `node tools/sanitize-for-public.ts`，再用 `--check` 复核（见上一节）。凭据之外，房间号/主播名/用户名/uid/观众弹幕同样是身份信息。
- **永不调用 `/user/export`**（它会输出含 cookie 的原始数据）。
- 所有出站文本（日志、错误报告、UI 报错）都经 `src/redact.ts`，禁止裸打印 request 对象。
- 版权：仅对**自己有权处理**的直播内容执行录制与二创投稿。
