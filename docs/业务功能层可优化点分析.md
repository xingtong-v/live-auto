# live_auto 业务功能层可优化点分析

> 纯分析报告，**未修改任何源码**。所有结论均给出文件 / 行号 / 函数名 / 配置项名。
> 证据基准：`README.md`（1408 行）、`src/*.ts`、以及**实机 `config.json` 的真实取值**（与 README 默认值不同，凡差异处已标注）。
>
> **硬约束口径**（本报告判定"是否冲突"的唯一标准，取自 README「硬约束（违反即返工）」表）：
> 只调用 biliLive-tools HTTP API、不 fork 上游（#1）；切片必须重编码但**由上游执行**（#5）；
> 不引入需原生编译的 npm 依赖（#9）；只监听 127.0.0.1（#2）；`dtime` > 提交时刻 + 7200s（#4）；
> 标签 1–10 / 标题 ≤80 / 简介 ≤250（#3）；`tid` 必须来自白名单（#16）；试跑期 `is_only_self:1`（#10）。
>
> ⚠️ **一条重要的边界澄清**：项目里"禁止自建编码"只针对**切片与压制链路**。本地 ffmpeg/ffprobe
> 早已被用于**分析与辅助**用途，且是既成事实：
> `src/speech-energy.ts:71`（解 8kHz 单声道算 RMS）、`src/asr.ts:580 detectSilence`（silencedetect）、
> `src/av-sync.ts:135`（流拷贝重挂）、`src/preview.ts:105-107`（**NVENC 真实重编码**试看片段）。
> 因此本报告里凡标"无硬约束冲突"的本地媒体分析建议，都以这四处为先例。

## 1. 半自动（默认）/ 全自动 的差异究竟体现在哪些开关上

### 1.1 唯一的模式闸门：1 行 3 个条件

全项目**只有一处**判定两种模式，就在 `src/daemon.ts:1337`（函数 `runPipeline`）：

```ts
const autoPublish = cfg.publish.autoPublish && !task.overrides?.skipAutoPublish;
if (!autoPublish) {            // daemon.ts:1339
  this.ledger.setStatus(taskId, 'ANALYZED', { stage: 'ANALYZED' });
  return { ok: true, stoppedAt: 'ANALYZED' };   // daemon.ts:1350
}
return await this.publishStage(taskId, log);    // daemon.ts:1354
```

三个条件的落点：

| 条件 | 位置 | 说明 |
|---|---|---|
| `publish.autoPublish` | `config.ts:372`（类型）、`config.ts:827`（默认 `false`）、`config.ts:946`（环境变量 `LIVE_AUTO_AUTO_PUBLISH`）、UI 开关 `ui.html:3289`、热切 `ui.html:4224` | 全局总开关 |
| `task.overrides.skipAutoPublish` | `types.ts:591`、`server.ts:1293`（`POST /api/task/:id/overrides`）、`ui.html:1218`（本场设置「跳过自动发布」） | **任务级反向覆盖** —— 全自动模式下的"这一场我要亲自看" |
| 状态机出口 | `daemon.ts:1339-1351` | 半自动 = **停在 `ANALYZED`**，不再往下走 |

### 1.2 差异的全部内容（就这些，没有第二处）

| 维度 | 半自动（`autoPublish:false`） | 全自动（`autoPublish:true`） |
|---|---|---|
| 分析之后 | 写 `ANALYZED` → 返回（`daemon.ts:1342/1345`） | **同一次 `runPipeline` 调用里直接进 `publishStage`**（`daemon.ts:1354`） |
| 谁触发切片 | 人工：`POST /api/task/:id/approve`（`server.ts:988`）→ `orch.publishStage`（`server.ts:1067`） | 无人：`runPipeline` 自己调 |
| 标题体检（error 级） | **强制执行并硬拦**：`server.ts:1033 checkClipTitles` → 有问题 `400 { error:'发布前校验未通过', problems }`（`server.ts:1062-1065`） | **不执行**。多分P 路径里只有 `publish.ts:2244 checkClipTitles`，注释明确"**只告警不阻断**" |
| 时长/时长范围、简介 250、标签 1–10、区间重叠检查 | `server.ts:1051-1061` 逐项校验后才放行 | 这些约束由 `analyze.ts:sanitizeClips`（`sanitizeTitle`/`sanitizeDesc`/`sanitizeTags`/重叠丢弃）在**分析阶段**保证，发布阶段不再复核 |
| 勾选来源 | 人工在 UI 勾 `clip.selected`（`server.ts:1147-1148`） | `analyze.ts:807-822` 按 **`autoSelectTopN` 相对排名**自动勾选（绝对分门槛 `autoSelectScoreFloor` 已证明失效） |
| 降级产出 | 停在 `ANALYZED`，等人工填标题 | `analyze.ts:1431` 把降级片段置 `selected:false` → **不会自动投**，等于自动退回半自动 |
| 通知 | `alert.ts:480 analysisDone`「等待确认发布」 | 同一条，但后面紧跟 `publishSuccess`（`publish.ts` → `alert.ts:495`） |

### 1.3 「自动化程度」其实由一组**互相独立**的开关共同决定

`autoPublish` 只是其中一环。以下每一项都能单独把"无人值守"打断或放大，**任意一个取错值，全自动就名不副实**：

| 开关 | 位置 | 取错值的后果 |
|---|---|---|
| `runtime.allowPaid` / `--allow-paid` | `config.ts:950`、`cli.ts:166` | `false` → 云 ASR 被硬约束 #14 拦住 → 空转写 → 全链路失败（`asr.ts:1067`）。**本地 ASR 不受此闸门**（`asr.ts:977 useLocalAsr` 短路，见 `asr.ts:1060-1088` 的注释） |
| `asr.provider` | `config.ts:91` | `bililive-tools` 时依赖**上游**里配好 ASR 模型，否则 `POST /ai/subtitle` 直接抛错 |
| `import.watch.enabled` + `import.watch.dirs` | `config.ts:271-302`、`daemon.ts` `WatchImporter` | 关掉后只剩 `recent-clips` 这一条腿，而它会**静默返回空数组** ⇒ 永不触发 |
| `publish.dailyLimit` | `publish.ts:1770-1789` | `0` = **关闭额度检查**（`quotaOn=false`），自动发布量只剩 `autoSelectTopN` |
| `publish.multiPart` | `daemon.ts:1462 useMultiPart` | `false` + `fullVideoBy='bililive-tools'` → `daemon.ts:1466` 直接抛 `StageError`；`config.ts:1037` 还会在配置校验报 error |
| `publish.fullVideoBy` | `config.ts:495` | `bililive-tools`（默认）→ 找不到它的稿件就**停在 CLIPPED 等**，最多 `resumeWaitMin`（默认 90 分钟，`daemon.ts:1593`） |
| `publish.immediatePublish` | `config.ts:535` | `true` → 不传 `dtime`，**放弃硬约束 #4 的错峰保护**（实机已 `true`） |
| `publish.isOnlySelf` | `config.ts:373` | `0` = 公开。自动发布的错误会**直接对外**（实机已 `0`） |
| `clip.autoSelectTopN` | `config.ts:318`、`analyze.ts:807` | 唯一的自动数量闸门；设很大 + `dailyLimit=0` ⇒ 一场有多少候选就投多少 |
| `clip.burnSubtitles` | `publish.ts:1443` | `false` → 转写只用于选片，**白花一次 ASR**（实机已 `false`） |
| `cleanup.deleteAfterUpload.enabled` / `graceHours` | `config.ts:555-573` | `true` + 0.5h → 上传确认后 30 分钟**永久删除源录播**（跨盘不进回收站，`README` L1141） |
| `runtime.maxParallelTasks` | `config.ts:909`（默认 1） | 场次级串行，队列积压时是吞吐上限 |

## 3. 业务功能层可优化点（全链路）

优先级判据：**高** = 直接影响成片质量/投稿安全/收入；**中** = 显著提升效率或可观测性；**低** = 体验优化。
成本判据：**小** = 单文件数十行；**中** = 跨 2–3 模块；**大** = 新增子系统或需上游配合。

### A. 录制 → 转写（信号与成本）

| # | 涉及文件 / 位置 | 现状 | 缺口 / 问题（含用户场景） | 建议方案 | 优先级 | 成本 | 硬约束 |
|---|---|---|---|---|---|---|---|
| A1 | `asr.ts:118-123 silenceTrim.enabled`（实机 **false**，`config.json:119`） | `detectSilence`（`asr.ts:580`）+ `buildSpeechPlan`（`asr.ts:650`）已实现，含 minChunk/maxChunk 与 padding，但默认关闭 | 本地 Fun-ASR 虽免费，但 RTF 0.168 → **4h15m 素材要 43 分钟**（README 实测表）。直播里纯游戏操作/长静默占比高，用户"切片等 40+ 分钟才出片" | 打开 `silenceTrim.enabled`；并把 `noiseDb` 从 -32 调到实测更合适的值（建议先跑一轮 `--dry-run` 对比 `audioSeconds`）。README「想省钱」节估 20–40% | 高 | 小 | **无冲突**（本地 ffmpeg 分析，已有先例 `speech-energy.ts:71`） |
| A2 | `config.json:109 segmentMinutes:60` + `asr.ts:962-1014` | Fun-ASR 走"大块+并行"，`chunkMinutes=360`、`parallel=1`（`config.ts:177-187` 注释：单 GPU 并行净收益为负） | **本地转写是串行长尾**：一场 4h 直播转写 43 分钟，期间该场占住队列（`runtime.maxParallelTasks=1`），下一场录制完成也只能排队 → 连播场景出片延迟累积 | ① 评估 `engine:'vllm'` 是否比 pytorch 快（`config.ts:151` 已有该旋钮）；② 让**转写与"下一场的录制完成判定"解耦**：转写期不阻塞 `trigger`（当前已解耦，但队列串行）；③ 多卡用户调 `parallel` | 中 | 中 | 无冲突 |
| A3 | `asr.ts:1244-1248`（覆盖率告警） | 只在覆盖率 <5% 且 segment 数 >0 时告警 | **5% 这个阈值过于宽松**：一场 4 小时直播转写覆盖 8% 也会被静默接受，选片几乎全靠弹幕，用户不会知道 | 改为分档告警（<5% error、<20% warn），并在 `clips.json` 上与 `degraded` 一起暴露到 UI 任务卡 | 中 | 小 | 无冲突 |

## 5. 结论与建议动手顺序

**一句话**：这个系统的**编排层已经相当成熟**（幂等、崩溃恢复、脱敏、回收站、918 项断言），真正的瓶颈全在**决策层的信息量**与**回流闭环的缺失**上。

按"投入产出比"排序的建议动作：

| 顺序 | 动作 | 依据 | 预期收益 |
|---|---|---|---|
| 1 | 打开 `clip.avSyncRepair`（`config.json:219`） | README ⑦b 实测 16 个成片中 7 个音画错位，最大 3.7s | 消除一个**正在持续发生**的已知成片缺陷，成本≈0 |
| 2 | 重估 `clip.burnSubtitles`（`config.json:200`），先跑 `tools/subtitle-burn-check.ts` | 当前已用 `local-funasr`（时间戳偏差 ±0.18s），关闭字幕的原始理由（云 ASR 窗口离谱）已消失；`subtitle-ass.ts` 882 行能力闲置 | 让已付费/已耗时的转写产出真正进入成片 |
| 3 | 恢复 `cleanup.deleteAfterUpload.graceHours` 到 ≥24（`config.json:310`） | 0.5h 等于取消第三层保护，跨盘源录播**永久不可恢复** | 消除一个不可逆的数据丢失风险 |
| 4 | 收紧 `maxDurationSec`（600 → 90–180）与 `dailyLimit`（0 → 5–10） | 与"切片"的产品定义冲突 + 额度闸门全关 | 投稿频率与内容形态回到健康区间 |
| 5 | 统一半自动/全自动的标题校验强度（D8/D9）+ 补 e2e 用例（F6） | `server.ts:1033` 硬拦 vs `publish.ts:2244` 只告警 | 让"全自动"不再是一条低门槛通道 |
| 6 | 给 select prompt 注入"候选附近的转写原文"（B1） | `analyze.ts:394-397` 自陈 LLM 看不到原文，为此写了三重事后补丁 | 从根上减少"切在半句话上"，可能让 `resolveClipEnd`/`detectSongRegions`/能量修正的补丁需求下降 |
| 7 | 回流只读闭环：把 `performanceView`（`server.ts:3238`）的聚合结果注入 select prompt（E1① + E2） | `analyze.ts` 对 `performance` **零引用**（已验证）；`daemon.ts:2884` 自陈只做拉取 | 让 30 场积累的数据第一次产生价值，成本小、不动阈值、可一键回退 |
| 8 | 补 `performanceAnomaly` 告警（F3）+ 监控面板"发布安全姿态"卡片（F5） | `alert.ts` 有 8 个语义化事件但无表现类；`config.json` 的危险开关组合当前**在 UI 上不可见** | 全自动模式下的故障从"第二天才发现"变成"小时级发现" |
