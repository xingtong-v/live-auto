## Bug #1【高危·正在复现】分页完整性判据被服务端截断击穿 → 误判「稿件已删除」

### 证据链（全部实测）

**① 代码发出的请求与服务端的实际返回不一致**

```
代码：client.biliArchives({ page: 1, pageSize: 100 })   ← daemon.ts:3656/3663、tombstone-reconcile.ts:69/119
实测：/bili/archives?page=1&pageSize=100&pn=1&ps=100
      → 只返回 10 条（响应里 page = { "pn": 1, "ps": 10, "count": 61 }）
```

**② 完整性判据因此恒为真**

```ts
listComplete = archives.length < PAGE_SIZE;        // daemon.ts:3674
listComplete = archives.length < TOMBSTONE_LIST_PAGE_SIZE;   // tombstone-reconcile.ts:131
// 10 < 100 → true ⇒ 代码认为「列表已拿全」，实际 61 个稿件里有 51 个看不见
```

**③ 于是「不在我的稿件列表里」这个前提是假的**

```
翻页取全（20/页 × 4 页）确认：账号实际有 61 个稿件
其中 BV1nMJy65E92 确实在列表里（第 1 页，状态=待发布 arc_audits）
但在 `pageSize=100` 的返回（只有 10 条）里**看不到它**
```

**④ 与「详情接口报错」叠加，得出「已删除」的错误结论**

```
00:58:30  [perf] ✗ GET /bili/user/archive/BV1nMJy65E92  → HTTP 500 body「啥都木有」
00:58:30  warn     稿件 BV1nMJy65E92 已不在稿件列表（被删或下架），已标记，不再反复拉取表现数据
00:58:31  warn     已人工解除墓碑（该录制区间现在可以重新投稿）：乙主播队伍追平比分…   ← 之后 18 次
…
00:58:34  共 18 条墓碑在这一轮被解除，依据全是：
          「旧稿件 BV1nMJy65E92 既不在我的稿件列表里，详情接口也明确报『不存在』（…啥都木有）」
```

### 影响（按严重度）

1. **重复投稿风险（最要紧）**：墓碑是「这段内容以前投过、别再投一遍」的防重复保险。18 条被误解除后，
   那些片段若重跑/重投，B站 上会真的多出一份重复稿件 —— 正是墓碑要防的事故。
2. **表现数据永久停拉**：`refreshPerformance` 用同一套判据，把 16 个 bvid 写进 `performance.jsonl` 的 `gone:true`；
   `bvidsNeedingPerformance` 见到它就跳过（除非它重新出现在列表里）。
3. **界面误导**：这些稿件在表现页会显示「稿件已不存在」。
4. **无谓请求**：同一 bvid 在一轮里被请求 19 次（见 Bug #2）。

### 根因与修法

| # | 根因 | 修法 |
|---|---|---|
| 1 | `listComplete` 拿**请求**的页大小比，而不是**服务端实际返回**的页大小/总数 | 用响应里的 `page.count`（61）与累计已取条数比较：`累计 >= count` 才算拿全。`api.ts` 目前把 `page` 元信息整个丢掉了，需要透出来 |
| 2 | 只取第 1 页，`pageSize` 大于服务端上限时静默降级（100 → 10） | 按 `count` **循环翻页**直到取全（项目里已有翻页先例：`daemon.ts:2442` 的 `for (page...)` 写法），并对每页实际条数做二次校验 |
| 3 | 「已删除」只凭详情接口 500 的 body 判定（`isArchiveGoneError` 里含 `啥都木有`） | 优先用列表里的 `state`（如 `-4 已锁定`、`-1 待发布`）；`啥都木有` 属 biliLive-tools 的通用「上游没数据」，未发布/仅自己可见/接口异常都会出现，**不能单独作为已删除的证据** |
| 4 | 自动解除打的是「已**人工**解除墓碑」 | 文案区分自动/人工两条路径（日志定位成本） |

### 回滚建议

`publish-log.jsonl` 的 `tombstone-release` 记录里带 `fingerprint / bvid / taskId / clipIndex / note`，
写一个 `tools/rollback-tombstone-release.ts`（按 `at` 区间 + `bvid` 过滤，把墓碑按原记录补回 `ledger.tombstones`）
即可精确回滚这 18 条；回滚后建议在台账里留一条「回滚原因」备注，避免下次核对又立刻解除。

## Bug #2【中】墓碑核对对同一个 bvid 重复请求 N 次（绕过了同文件的详情缓存）

**位置**：`src/tombstone-reconcile.ts:187`

```ts
let verdict: 'gone' | 'alive' | 'unknown' = 'unknown';
try {
  await client.biliArchiveDetail(t.bvid, { retry: 0 });   // ← 直连，没有走上面的 detailCache / partsOf
```

同一个文件里已有 `detailCache`（`tombstone-reconcile.ts:137`）给「分P标题扫描」用，但 bvid 判定这条路是直连的 →
**18 条墓碑共用一个 bvid，就发 18 次请求**（实测 19 次/4 秒，间隔 ~150ms）。

**影响**：无谓请求 ×N（N = 该稿件关联的墓碑数）；对 B站 / biliLive-tools 是"短时间重复打同一接口"，与项目里
「低频率、只读接口，无风控压力」的设计前提相冲突；日志噪音掩盖真问题。
**修法**：这条路改走 `partsOf()`/`detailCache`（同一 bvid 整轮只查一次）。

## Bug #3【低】请求日志 tag 误导排查方向

`src/api.ts:777` 把 `tag: 'perf'` 硬编码在 `biliArchiveDetail()` 里，于是**墓碑核对**发出的请求在日志里也写成
`[perf] ✗ GET /bili/user/archive/...` —— 排查时会把「表现数据回流」与「墓碑核对」两条链路混成一条
（本次排查就先被带偏过一次）。
**修法**：`tag` 由调用方传入（`biliArchiveDetail(bvid, { tag })`），或分两个方法。
